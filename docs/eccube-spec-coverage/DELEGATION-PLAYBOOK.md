# テスト実行を AI に委譲するプレイブック

EC-CUBE 結合試験 × BeMart カバレッジ調査で得た、**テスト実行を別のエージェントに委譲する**ときの再利用可能な型。安価な **executor**（証拠採取）＋強い **verifier**（判定）に分けて回す前提。
BeMart 固有の道具——[`harness/`](harness/)・[`EXECUTOR-BRIEF.md`](EXECUTOR-BRIEF.md)・[`VERIFIER-BRIEF.md`](VERIFIER-BRIEF.md)——はこの型の具体実装。

## 原則

1. **証拠の無いテストは主張にすぎない。** 項目ごとに **スクショ（人の直感判断）＋ DOM（機械照合）** を必須にする。無いと、人もモデルも一番安い緑信号（HTTP 200）に流れる。
2. **成功条件を機械的に固定する。** 「200 が返った」ではなく「**期待結果が証拠に写っている**」を done とする。`HTTP 200 ≠ 期待結果`。逃げ道を指示の中で塞ぐ。
3. **「やってない」と「できない」を分ける。** 最大の lever。未エンコードの作業を system の限界とすり替えさせない。本物の不能（501／要素が存在しない／前提が物理的に作れない）だけが「発見」。「ステップを書かなかったから false」は未完成であって結果ではない。
4. **推測させず、現物を辿らせる。** URL／セレクタの推測は 404 の元。「一覧の実リンク・実 DOM を辿れ」と手段を限定する。
5. **発見コストは一度きり。共有資産化して二度払いしない。** 認証・PRG（`200+Location`）・フォーム prefill・ルート・seed データは一度掘ったら **テンプレ／brief／seed** に格納。"1個1個 地獄" の正体はこの一度きりの探索摩擦で、委譲先の能力税ではない。

## メタ：委譲先の質より、委譲インターフェースが効く

良い基準（criteria）＋共有文脈（context）＋証拠チャネル（evidence channel）さえあれば、安価な executor でも十分に働く。実際この調査では、安価モデルが——正直に false を報告し、スクショで見落とした不具合（ヘッダのカートバッジ未更新）を DOM から拾い、データ起因（`sale_type_id NULL`）を自力で診断し、ログインフォームを自分でデバッグした。**委譲先を見下さず、直すべきは指示**。

## 新しいアプリに適用するには

1. **証拠チャネルを決める** — 項目ごとに `png + html + http_status` を JSONL 1行で。`verifier_status` は executor 側では `null` 固定。
2. **executor と verifier を分離** — executor は事実だけ記録、判定（カバー率）は verifier。証拠が両者のインターフェース。
3. **導線を一度掘ってテンプレ化** — 認証・多段フロー（このプロジェクトなら [`harness/scenarios-checkout.json`](harness/scenarios-checkout.json) のゲスト購入）を再利用テンプレに。各項目は「値の差し替え」だけの小変種にする。
4. **executor 用 brief に明記** — ①証拠必須 ②「やってない≠できない」 ③推測禁止 ④seed 済みテストデータを使う。
5. **領域ごとにバッチ＋スポット検証** — 一気に全件回さず、領域単位で要約を出し、系統的ミスを早期に検出。
