# BeMart Entity ↔ EC-CUBE 4.3 MySQL Schema Diff

Source schema: `sql/schema/bemart-schema.sql` (65 tables: 43 `dtb_*` + 22 `mtb_*`, authored from first principles against the EC-CUBE 4.3 structure).
BeMart Entities: `be/src/Reason/Entity/*.php` (34 files).

## Global notes (apply once, then ignored per-row)

- **`discriminator_type` column** — every table carries `discriminator_type varchar(255) NOT NULL` for Doctrine STI in EC-CUBE. Phase 2b must populate it with the bundled entity class FQCN (e.g. `Eccube\Entity\Customer`) on INSERT but BeMart never reads it. Treat as an opaque write-through constant per table.
- **No `del_flg` column.** EC-CUBE 4.3 has NO soft-delete column. Logical deletion uses status enums per table:
  - Customer: `customer_status_id` FK → `mtb_customer_status` (1=PROVISIONAL, 2=REGULAR, 3=WITHDRAWN)
  - Product: `product_status_id` FK → `mtb_product_status` (1=VISIBLE, 2=HIDDEN, 3=WITHDRAWN — matches BeMart `ProductEntity::STATUS_*`)
  - Member (admin): `work_id` FK → `mtb_work` (0=inactive, 1=active — matches BeMart `AdminEntity::WORK_*`)
  - Order: `order_status_id` FK → `mtb_order_status`
  - Most CRUD master tables (`dtb_block`, `dtb_layout`, `dtb_delivery`, `dtb_payment`, `dtb_class_name`, `dtb_class_category`, `dtb_delivery_time`, `dtb_news`) carry a `visible tinyint(1) NOT NULL` for soft-hide.
- **`creator_id` audit columns** — many `dtb_*` tables carry `creator_id int unsigned NULL` FK → `dtb_member(id)`. BeMart entities do not model this; Phase 2b must default it to NULL or to a system-admin id on INSERT.
- **`create_date` / `update_date`** — almost every table has both, with comment `(DC2Type:datetimetz)`. BeMart Entities almost never expose them — Phase 2b must populate from a clock (NOW()) on every write.
- **Charset / collation.** All tables use `utf8mb4` / `utf8mb4_bin`. BeMart string fields therefore use binary-collation comparisons by default (case-sensitive LIKE). Filter searches (Customer, Product, Admin) should use `COLLATE utf8mb4_unicode_ci` explicitly if case-insensitivity is desired.
- **Identity types.** EC-CUBE `id` columns are `int(10) unsigned NOT NULL AUTO_INCREMENT`; master tables (`mtb_*`) are `smallint(5) unsigned NOT NULL` (no autoincrement, fixture-seeded). BeMart entities use `string` for opaque ids (hex tokens generated by `*IdProviderInterface`). Phase 2b must decide: keep BeMart's hex tokens in a separate `external_id` column, or accept the bigint-autoinc and surface it as a stringified int. The cleanest path is to **add a `bemart_external_id varchar(64)` column to each touched table** for the opaque handle, indexed UNIQUE.
- **EC-CUBE FK fan-out** is far wider than BeMart's flat shape. Customer, Order, Shipping all reference `mtb_pref`, `mtb_country`, `mtb_sex`, `mtb_job`. BeMart treats `pref` / `sex` / `job` as raw ints (the master `id`). Phase 2b can keep these as raw FK ints — no additional mapping needed — but admin filter queries may need joins for human-readable labels.
- **Money columns** are `decimal(12,2) unsigned` (price totals) or `decimal(12,0) unsigned` (points). BeMart entities use `int` for both. Phase 2b must guard against fractional yen in `subtotal/total/payment_total/charge` (round at the storage boundary) and against signed overflow (BeMart `int` is signed; EC-CUBE is unsigned).
- **Datetime columns** use MySQL `datetime`, not `timestamp`, and the `DC2Type:datetimetz` comment hints Doctrine round-trips with a timezone offset stored in a sibling string column — but the real 4.3 schema **does NOT have that sibling column**. The TZ-suffix is implicit (server tz). BeMart entities expose timestamps as `string` ISO-8601 or `DateTimeImmutable` (PasswordResetTokenEntity). Phase 2b: serialise to MySQL `Y-m-d H:i:s` in UTC.

## CartEntity → dtb_cart (+ dtb_cart_item)

**Match grade**: B (composite — header + items)

**Field map (header → dtb_cart)**:

| BeMart field | EC-CUBE column | notes |
|---|---|---|
| cartKey | cart_key | varchar(255) NULL — BeMart uses non-null |
| saleTypeId | (no direct column) | EC-CUBE encodes saleType inside `cart_key` suffix in production; BeMart already splits it out |
| saleTypeName | (derived) | join via dtb_product_class.sale_type_id → mtb_sale_type.name, or derive from CartItem |
| items | (rows in dtb_cart_item WHERE cart_id = dtb_cart.id) | 1:N |
| totalPrice | total_price | decimal(12,2) unsigned — int truncation hazard |
| deliveryFeeTotal | delivery_fee_total | decimal(12,2) unsigned — int truncation hazard |
| preOrderId | pre_order_id | varchar(255) NULL, UNIQUE — BeMart non-null |

**Mismatches / gaps**:
- EC-CUBE `dtb_cart` has `customer_id`, `sort_no`, `add_point`, `use_point`, `create_date`, `update_date`. BeMart `CartEntity` has none of these.
- `saleTypeName` is derived — Phase 2b SELECT joins `dtb_cart_item → dtb_product_class → mtb_sale_type`.
- `saleTypeId` is BeMart-explicit; EC-CUBE has no `sale_type_id` column on `dtb_cart` — it lives on `dtb_product_class`. **Hazard**: in EC-CUBE, a Cart row aggregates items that all share one saleType (enforced by `CartService`). The BeMart schema would store the dedup'd saleTypeId on the header for cheaper reads. Either (a) accept the join cost, or (b) add a `sale_type_id` column.

**Used by**: `CartQueryInterface::byCartKey`, `bySessionPrefix`; `CartCommandInterface::save`, `clearByPreOrderId`, `clearBySessionPrefix`.

**Phase 2b SQL surface**:
- SELECT cart + items WHERE cart_key = ?
- SELECT … WHERE cart_key LIKE 'prefix\_%' (the underscore is the literal separator)
- INSERT … ON DUPLICATE KEY UPDATE for the header; per-row REPLACE for items
- DELETE WHERE pre_order_id = ?
- DELETE WHERE cart_key LIKE 'prefix\_%'

**Hazards**:
- `cartKey` prefix scan — the `'prefix_%'` LIKE pattern requires escaping any user-influenced sessionPrefix.
- `dtb_cart_item.cart_id` has `ON DELETE CASCADE` — deleting the header automatically drops items. Use this.

## ContactEntity → (no table)

**Match grade**: D

**EC-CUBE 4.3 has NO `dtb_contact` table.** Confirmed by `grep contact` returning zero matches on `CREATE TABLE`.

EC-CUBE handles the customer-inquiry form by emailing the shop directly (Symfony `MailerInterface`) and does not persist. BeMart docstring on `ContactEntity` already calls this out: *"Held only long enough for the mail bodies to be rendered; not persisted in the Be-Framework layer (Phase 2 may add `dtb_contact` INSERT in the same Final)."*

**Recommendation for Phase 2b**: keep purely in-memory / transient. If persistence is desired, add a new `dtb_contact` (Phase 2b is observation-only, so this is a Phase 2c+ decision).

1. `dtb_member`: add `email varchar(255) NULL`, add `UNIQUE KEY (login_id)`.
